# 患者本人登记与就诊服务

## 首次就诊

微信登录后可先浏览营业门店、治疗项目、医生与真实可预约时间。提交预约前填写本人姓名、出生日期及联系电话，地址、紧急联系人和邮箱可后补；如实声明过敏情况并确认本人使用。系统生成患者编号，同事务新建Patient、建立当前本人关联并保存声明来源，无需已有患者编号、短信或人工批准，即可继续预约。

登记来源为SELF_DECLARED，Patient.allergy_review_status保持NOT_REVIEWED；本人声明保存于既有身份关联依据JSON，SD1为服务端声明快照，不冒充AR1医护核实，不新增临床过敏记录。APPROVED在该分支表示接纳登记，历史reviewed_by/verified_by字段记录实际登记主体，不表示人工核验。

## 已有档案与访问边界

已有档案使用独立安全关联流程，授权前台核实线索及本人身份后办理。姓名、电话匹配不能自动认领旧病历；重复线索只返回通用提示，不覆盖、合并或泄露已有资料。当前本人关联双向唯一；换号、重绑及撤销均留痕，旧会话立即失去原档案权限。已关联账号不必重新登记。

## 预约与页面

首页突出门店、服务和预约入口，预约依门店、项目、医生、日期及真实候选完成；提交重新核对排班、资质、执业、时隙占位与当前本人权限。我的分别显示微信会话、本人资料状态及预约记录；取消预约按原时间和状态限制执行，管理端与患者端读取同一后端数据库。

管理端主导航承担日常业务，齿轮独立提供系统配置、基础数据及权限管理。排班采用每周概览和按日医生视图，保留真实筛选、详情、新增、停诊及受影响预约处理。业务库24张表、209字段和44外键，现有技术存储与身份访问边界保留。

当前虚构测试门店支持标识清楚的演示挂号费、诊疗账单缴费和全额退款，不扣真实款；INVOICED表示已生成费用凭据，不表示付款。

## 真实微信支付：后续变更设计

### 账单

- 从已完成诊疗及唯一费用凭据产生可缴费用，不把治疗项目目录价或预计预约费用当作应收账单。
- 现有 Invoice／InvoiceItem 保存历史费用快照；INVOICED 继续表示已生成费用凭据，不改成已付款。
- 首期建议只支持本人诊疗账单全额微信支付；不新增预约挂号费、预交金、储值、医保或折扣。
- 患者仅查询、支付当前有效绑定的本人账单；管理端按门店及收费权限查看支付和退款事实。

### 支付

1. 服务端读取原账单金额，创建唯一商户订单；金额及账单归属不由小程序传入后直接采信。
2. 服务端下单后返回小程序支付参数；用户确认后调用实际微信支付。
3. 客户端成功回调只显示“正在确认支付结果”。以服务端验签、解密的通知或主动查单为准，校验商户、应用、金额、币种及订单归属。
4. 支付中的重复点击、通知重放、超时和关闭订单均保持幂等，不能重复收款。未知结果先查单再处理，不能新建订单掩盖原订单。
5. 支付事实和业务可见状态可靠落库；失败可重试，取消支付不取消诊疗预约、不撤销费用凭据。

### 退款

- 退款由获授权收费岗位发起并记录原因；不把患者取消预约自动等同于退款。
- 首期建议仅支持核实后的整单原路退款，累计退款不能超过已确认收款；部分退款作为后续单独范围。
- 区分申请、处理中、成功及失败，服务端通知／查单确认最终结果；重复提交及通知重放不重复退钱。
- 原费用凭据、治疗记录、支付与退款历史保留。经营分析继续沿原开票口径；收款及退款另列，不能悄悄改变既有季度绩效算法。

### 必需的实施前条件

- 确认商户主体、真实微信支付商户号、小程序 AppID 关联、商户 API 凭据、通知域名及支付能力。备案通过不等于支付已开通；本轮未收到或验证支付商户配置。
- 真实订单、支付尝试、通知处理及退款需要独立持久化事实。当前独立费用表已保存演示支付事实；真实商户接入仍须单独配置、扩展渠道处理并验收，不挤进Appointment状态或将Invoice当作已支付。
- 定向更新 Constitution 的“禁止支付”范围、Spec UC04／身份权限、接口契约及任务；原来 T050/T051 通过不代表支付通过。新增条目单独验收，不回填旧任务为已经完成。
- 验收包括真实小额支付／退款、重复通知、伪造客户端成功、金额错误、越权账单、换绑后旧账号、未知结果、订单关闭竞态、两端一致及故障恢复。真实商户未接入时明确显示演示支付且不扣真实款，不把演示记录当真实收款。

验收证据：docs/verification/patient-onboarding-20261124/README.md。手机确认覆盖新版可见及可进入预约，不扩大为真机首次登记或支付验收。
