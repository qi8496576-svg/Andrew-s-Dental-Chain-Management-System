# 患者预约精简与费用服务方案

状态：负责人于2026年11月25日批准以下最小范围调整，并选择演示支付闭环。实施及实测结果逐项记录；真实微信支付不在本轮上线范围。ERD先交付独立预览，得到确认后才能替换正式图源，保留原配色、分区、布局及简洁直线。

## 最短预约流程

门店与就诊需求 → 医生与真实时段 → 确认本人及费用 → 有收费时办理缴费 → 预约结果。

患者默认选择“看牙检查”，明确包含“不清楚具体问题，先由医生检查”；“洗牙洁牙”单独提供。专业治疗目录收在“其他明确服务”内，不要求患者自行诊断。入口映射后台启用的真实治疗项目，不生成项目或时隙；未配置对应项目时明确提示门店维护。实际治疗及诊疗收费以医生到诊后记录的事实为准。

已登记者不重复填资料。首次登记建议仅填写姓名、出生日期、联系电话、过敏声明及本人确认。联系电话用于门店联络与改期通知，建议保留；其本身不代表实名核验。地址、邮箱与紧急联系人退出首次预约必填步骤，后续确有需要再由本人或授权前台完善。登记返回后重新核对并恢复原选时段，避免患者手工重复检索；时段失效则要求重新选择。

## 已批准的数据调整

现有Patient将billing_address、emergency_contact_name和emergency_contact_phone均设为NOT NULL，并在前后端必填校验中使用；要真正移除首次填写要求，需要把这三列改为可空，并同步登记、预约、维护及响应契约。phone保持必填，email保持现有可空。缺失值保存NULL，不填假地址或虚构联系人，不复制本人的联系方式冒充紧急联系人。

Dentist增加可空的professional_title、specialty和introduction，分别表示职称、主要方向及个人简介。管理端提供编辑及患者可见预览；医生列表和预约卡片使用同一数据。职称与专业资质、执业权限分开，不能从任职年限或姓名猜测。未维护信息显示“暂未提供”，不默认赋予主任医师。演示医生的职称及简介明确属于虚构测试资料。

收费需要独立持久化事实，建议最小新增范围为：

| 数据 | 责任及约束 |
| --- | --- |
| RegistrationFeePolicy | 门店与医生的挂号费配置；金额为分，默认未配置时不收费，价格调整只影响之后新单。不得直接套用参考医院价格。 |
| BookingHold | 收费预约的短时号源保留，独立于原Appointment五状态；支付前复核排班、资质及占用，过期释放，不写成爽约。 |
| PatientBill | 本人挂号费或诊疗账单；关联患者、门店、号源或就诊、费用凭据及金额快照，区分待缴、已缴、关闭及退款状态。 |
| PaymentOrder | 服务端生成的支付订单、金额、渠道、演示／真实模式、状态及幂等信息；一笔账单不能重复成功付款。 |
| RefundOrder | 全额退款申请、原支付单、原因、操作者及结果；重复办理不重复退款。 |

这会改变原有“19业务表不变”“预约前资料完整”“不含挂号费和支付”的限制，需要定向更新Spec、接口、ERD及对应任务后实施，保持同一后端与数据库，不重构为新架构。

## 虚拟项目的缴费闭环

推荐本轮先实施清楚标识的演示支付：账单、订单、支付结果和退款记录真实落库，两端同步；页面始终显示“演示支付，不扣真实款”，不调用微信扣款，不冒充微信支付成功，也不计入真实收款或原R1收入。演示能力仅对明确的测试门店和受控配置启用。

挂号费由管理端配置，患者在确认页看见医生、时段、费用明细及总额。收费号源先短时保留，演示成功后才正式建立预约；取消演示支付或超时仅关闭保留，不制造成功预约或爽约。正式预约后的取消仍遵守原时间、状态和权限限制，退号与退款分别留痕；门店停诊或支付成功但未能预约时进入原路退款处理，不重复收款或新建虚假预约。

诊疗费用从已有Invoice及InvoiceItem形成独立待缴账单，不把目录价或预计费用当作已发生诊疗。INVOICED仍表示已生成费用凭据，与已付款区分。小程序增加“我的费用”，按待缴、已缴和退款组织；管理端查看同一账单和结果。

## 真实微信支付

真实支付使用独立模式及微信支付服务端适配，要求可用商户号、与小程序的关联、已开通支付权限及受控密钥配置。金额和账单归属由服务器校验；客户端回调不作为收款依据，通知验签／解密或主动查单确认最终结果。退款、超时、重复通知、未知结果及并发均须实际验收。演示通过不代表真实微信支付已经开通或验收。
