## 环境准备和隔离

1. **Windows 宿主**保留当前原始文档和图源原位，运行微信开发者工具；Java、Maven、Node 可在 Windows 使用。若选用 WSL2，启用 Docker Desktop 的 **WSL2 engine** 和 Linux containers，并确认所用发行版的 WSL Integration。不能把 Docker VMM 模式与 WSL2 engine 混为一谈；前者的 WSL socket 能力不同，不能据其 CLI 可用推定 Testcontainers 可用。
2. **代码目录**由后续实施建立，不移动或覆盖原始 Word、UML、ERD 或归档。WSL2 大量 bind-mount/热更新工作可用独立 Linux 文件系统开发检出；当前 D 盘工作目录也可用于构建，但必须记录跨文件系统 I/O 差异，不以其耗时替代 Q03。
3. **数据库**本地及集成均为 Linux MySQL 8.4 / InnoDB，与生产版本线保持一致；不使用 Windows 原生 MySQL 或内存数据库替代锁/大小写/唯一键验证。初始化统一 `lower_case_table_names=0`，已有数据目录不得通过修改该参数“修复”映射问题。
4. **数据库范围**为 `adc_business`、`adc_identity`、`adc_audit` 三个物理schema，依 [research.md](research.md) 分离职责并保持同实例。业务schema仅原24表；identity明确13张技术表、audit明确1张。adc_control/meta职责并入identity，不创建旧名物理库；完整表/字段/键见[技术模型](technical-data-model.md)。开发、集成、基准、恢复演练分别使用隔离实例或隔离持久卷及配置，不共用正式数据。
5. **配置与秘密**：数据库连接和目标 schema、业务时区、允许来源、微信 AppID、会话配置及秘密文件路径由环境提供；数据库口令、AppSecret、上传密钥、会话令牌和初始管理凭据不写入代码、仓库、镜像、前端配置或日志。开发用秘密为本地受控文件，生产用受控秘密注入；不在文档中放真实值。
6. **微信联调输入**由负责人提供或确认测试 AppID、开发者成员资格、服务器域名、HTTPS 证书和相应平台配置。生产路径必须使用真实 `wx.login` / 服务端 `code2Session`；开发测试适配器只允许隔离测试配置，不作为真实微信登录成功证据，也不能在生产中启用。网络准入规则在真实联调时按微信后台当前要求复核。

开发环境可只配置本地 API 代理及必要端口；管理端最终通过同源反向代理访问 API，小程序使用登记的 API 地址。前端只做输入、结果展示和交互；可信主体、患者绑定、岗位/诊所权限、状态、金额及 R1 均由后端判定。

## 实施后启动约定

下面命令引用的文件和脚本**目前不存在**。Tasks 必须为这些入口建立实现及验证责任，创建后使用锁文件和固定版本执行；不得临时改成不受控的 `latest` 依赖来绕过兼容问题。

### 数据库与后端

从项目根目录运行计划中的开发 Compose，先只启动隔离数据库：

```powershell
docker compose -f ops/compose/compose.dev.yml up -d mysql
docker compose -f ops/compose/compose.dev.yml ps
Set-Location -LiteralPath 'backend'
.\mvnw.cmd -Pdev spring-boot:run
```

WSL2/Linux 在 `backend/` 下使用同一 Maven 配置：

```bash
./mvnw -Pdev spring-boot:run
```

期望：数据库通过就绪检查，后端使用 JDK21、Spring Boot4.1.2、MyBatis Starter4.1.0（MyBatis-Spring4.1.0、MyBatis核心3.5.19） 启动，连接正确的隔离实例，应用和数据库会话时间点使用 UTC。开发迁移只应用到允许的隔离目标；启动前按 [data-model.md](data-model.md) 对照 24/209/44 基线，发现结构漂移不得自动覆盖原结构。迁移历史写入 `adc_identity.flyway_schema_history`；不得借工具默认行为在 `adc_business` 新建历史表。

后续实现须为开发/测试提供明确的虚构数据准备入口或测试 fixture，并在 Tasks 指定命令和位置；本轮不虚构已存在的 seed 脚本。初始总部账号采用受控初始化流程，首次凭据由秘密渠道取得，不提供公开注册总部权限或写死的通用管理员口令。

```bash

```

## 虚构验收数据集

测试数据必须全部虚构，不复制真实患者联系方式或临床资料。以可追踪版本标识数据集，固定业务时区 `Asia/Shanghai`、稳定业务编号与记录关系；账号秘密与数据文件分离，不写入公开测试输出。数据准备不得通过直接把状态改为 INVOICED 来绕过待验证的主流程。

| 数据集 | 最少覆盖内容 | 目的 |
| --- | --- | --- |
| 正常业务链 | 两家诊所、两位牙医、完整/缺失必需资质、有效/失效执业、正常/挂起/相邻/跨诊所重叠班次；两位患者及过敏三态；检查、咨询、收费与零价项目 | 覆盖资源→排班→患者→预约→到诊→诊疗→开票；区分期望与实际治疗、预约牙医与实施者。 |
| 身份权限 | 患者甲/乙的独立主体，患者甲换号后的新主体；分诊所前台/收费/牙医账号，具有不同总部能力的账号，普通及审计权限账号 | 验证本人隔离、诊所范围、字段最小披露、分权、重绑唯一及即时失效。 |
| R1 核算 | 已结束自然季度、季度边界开票与成本，在职/离职/无收入及此前离职但本季仍有归属者；封账/零成本确认及缺失变体；直接成本、公共费用、冲销、有效分钟及停诊时长 | 核对人员、归期归属、守恒、尾差、零负激励、不完整禁发和版本切换。 |
| 并发与故障 | 同一时隙争用、同键重试和同键异内容、到诊/爽约竞争、重复开票、改约两端失败、首次/替换发布并发、审计保存失败 | 以真实 MySQL 证明互斥、唯一、事务及回滚，不能仅靠 Mock。 |

测试中的服务端时钟控制仅属于隔离测试设施，不能暴露为生产用户可更改的业务参数。对取消开始/结束边界、自然季度、空闲30分钟、绝对8小时和认证失败15分钟限制，分别保留边界前后样本及期望结果。

### 性能基准

30诊所、100牙医、1万患者、10万预约、20万治疗。隔离Linux容器合计CPU上限2核、内存上限2GB，独立负载进程；10并发持续20分钟，每用户约2秒一次请求，候选检索/治疗保存/结算占60%/20%/20%。另在现有2核2GB云端执行5并发5分钟只读验证。隔离测试不少于5000次实际成功请求，各类P95≤3秒，非预期错误率<1%，配比误差≤0.5个百分点；云端不少于600次只读请求，P95≤3秒且错误率<1%。保存原始样本、资源和落库核对，不推断100并发或云端大规模写入容量。

在项目根目录使用Node24执行 `node tools/verification/run-q03-small.mjs`。运行器没有外部数据库参数，只新建带随机标识的隔离MySQL、应用和HTTPS代理；使用现有34份迁移及受控生产应用镜像。数据库896MiB/1核、应用768MiB/0.9核、代理96MiB/0.1核，禁用容器交换扩容，合计1760MiB/2核。Windows k6负载进程在这些容器外运行。准备阶段按500行提交夹具，正式窗口逐次通过真实账号、会话、岗位和诊所权限执行API。

`node tools/deployment/verify-q03-cloud-read.mjs` 使用受控前台账号，对现有正式HTTPS执行5并发5分钟只读访问；保留正式证书验证，不调用业务写入API。登录及授权读取正常产生安全审计。

结果位于docs/verification/performance。逐类核对请求数、比例、P95、错误、实际新增治疗、费用凭据/明细、状态事件、审计及幂等回执；记录容器CPU/内存限制、采样、OOM及重启次数。隔离HTTPS仅使用一次性测试证书，证书例外限该本机测试，正式云端必须通过证书校验。未知写入结果只按原键核实，不重放旧结果填充负载。此标准适用于当前小规模部署，不承诺100人并发或云端全规模写入。

### 备份与恢复演练

按 [research.md](research.md) 及后续 `ops/backup/` 工具建立每日一致全备、最长未归档跨度≤15分钟的连续binlog增量，保留至少可恢复30天的全备与日志链。备份清单包含所有schema、数据库版本、全备时间、共同日志恢复坐标、校验摘要和所需配置/秘密恢复途径；存于独立备份介质，不能只留在数据库同一宿主卷。审计在线保留1年与备份30天分别执行，不把两者混为删除期限。

现有ops/backup脚本提供“备份清单校验”“恢复到指定坐标”“业务一致性核对”入口，并在Tasks明确实际命令；实际执行入口见ops/runbooks/recovery.md及Verify-Recovery.ps1。演练从取得备份开始计时，在全新隔离目标恢复所有schema到同一共同位点，禁止拼接不同截止时点；核对：

- 原24表/209字段/44外键、条件及跨表不变式与关键数量；
- 开票总额、成本净额、R1分摊守恒、历史版本及每人每季唯一当前发布；
- 就诊状态/事件、取消分类及改约来源链；
- 当前一对一绑定、失效旧绑定、账号停用、授权及撤权、审计引用；
- 幂等回执与业务结果一致，恢复后原键重试不重复造预约或单据；
- 实际丢失时间跨度≤15分钟、总恢复耗时≤4小时，保留实际计时及核验结果。

不能打包正在写入的裸数据卷宣称是一致备份，不能以“存在备份文件”代替恢复验证。恢复演练失败时停止放行相关环境，保留备份链和失败证据，修正方案后重做；不对原工作区或正式实例执行清空、覆盖、恢复或卷删除。

## 证据、故障定位及退出条件

每项记录AC编号、关联UC/SF/Q/R1、源码/契约版本、操作主体与范围、虚构数据版本、环境、前置、步骤、期望与实际、原始结果位置、核验人及结论。请求标识可用于追踪，但令牌、密码、AppSecret及无关完整临床资料不得进入日志或测试报告。

常见失败按边界定位：Docker只有客户端无服务端或WSL socket不可用时先修环境；表名大小写/字段数不符时先核对原字典与LinuxMySQL初始化；`npm ci`失败先核对Node/锁文件，不能删除锁文件掩盖冲突；微信仅开发工具可用时复核真实配置，不能将测试身份适配器放入生产；幂等/锁/回滚失败时保留同一请求键与事务证据，不以新键重试掩盖问题。

本地验证结束只停止本次隔离服务并保留数据/证据，不自动删除持久卷，不混用生产配置。该指南的验证步骤全部通过、适用Q目标具备真实证据且负责人完成对应审核后，才可形成对应功能验收结论；本次Plan不作这些通过声明。当前Plan已批准，C-04真实微信配置/联调及C-05云资源/性能/恢复转后续实施及验收，C-03保留必要工具验证；指南命令不代表运行通过，见[批准记录](plan-approval.md)。
