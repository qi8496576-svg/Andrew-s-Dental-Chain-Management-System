# ADC 身份 授权与审计契约

日期：2026-11-07。状态：Plan 阶段设计，尚未实现或执行验收。依据：[研究决策 R-D02—R-D04](../research.md)、[Spec](../spec.md) 的 FR-013—016、FR-018—021、Q06—Q08、Clarifications Q1，以及原表 B12a、B12b、D26。本文的技术记录不属于新增业务用例或业务表。

统一路径前缀为 `/api/v1`。路由、字段结构和公共错误格式与 [业务接口契约](api.md)、[OpenAPI](openapi.json) 共同阅读；本文补充可信输入、状态、权限、原子性及失败语义，不授权客户端自报身份或直接修改业务状态。标识符使用字符串，时间点使用带时区的时间格式，存储按 UTC；权限有效时点由服务端判断。

## 组件与存储边界

首版采用同一 Spring Boot 后端进程中的独立身份、授权、审计模块；不引入 Keycloak、Redis 或独立身份微服务。Java/Spring 的具体版本线、成熟密码散列库及数据库选择以 research.md 为准。

| 存储边界 | 责任与技术记录 | 不得越过的边界 |
| --- | --- | --- |
| `adc_business` | 原 Patient、Clinic、Dentist、Appointment 等全部 24 张业务表 | 保持 209 字段、30 外键；不能增加登录字段、角色字段、身份锁表或迁移历史表。 |
| `adc_identity` | Subject、ExternalIdentity、StaffAccount、Session、LoginThrottle、BindingRequest、CurrentPatientBinding、BindingEvent、AccessGrant、GrantClinicScope、GrantCapability、RequestReceipt、flyway_schema_history，共13表 | 非牙医员工不伪造为 Dentist；主体与业务患者/诊所/牙医的引用需应用层验证，不为技术组件新增业务外键。 |
| `adc_audit` | AuditEvent，1张只追加可信审计表 | 普通运行凭据没有修改或删除审计的权限；受控保留流程不能使记录在规定的 1 年内丢失。 |
| 原 `adc_control` / `adc_meta` | 不创建物理schema，分别落 adc_identity.RequestReceipt / adc_identity.flyway_schema_history | 模块职责保留；不替代业务证据；工具历史写权仅给migrator。 |

原D1仅为业务ERD；新增[技术模型](../technical-data-model.md)含14张技术表及字段、19条技术FK和12项应用引用。技术→Patient/Clinic/Dentist不加物理FK，由服务验证；技术内部关系有明确FK。

这三个物理schema位于同一 MySQL 主实例，关键操作必须使用同一个连接、同一显式事务及 InnoDB。模块独立不意味着各建连接各自提交；若以后迁至不同实例，须重新评审事务和恢复方案，不能沿用“跨 schema 本地事务”的结论。

内部主体是身份组件生成的长期标识 `subject_id`，不是客户端传入的患者主键、手机号、微信会话密钥或用户可编辑昵称。微信外部身份通过 `(provider, appid, openid)` 唯一关联内部主体，外部标识按原值精确比较，不擅自转小写或用不区分大小写的比较合并；不得自动按 `unionid`、姓名或电话合并患者。

## 会话与浏览器请求约束

| 客户端 | 会话签发与携带 | 保护规则 |
| --- | --- | --- |
| 微信小程序 | 真实微信代码交换成功后签发 ADC 不透明 Bearer 会话；令牌仅用于请求头 | 会话签发时服务端固定为小程序客户端类型；不能接受客户端 `X-Client-Type` 等值改变会话类型。AppSecret、`session_key` 不下发，也不当作 ADC 会话令牌。 |
| 员工 Web | 员工凭据验证成功后设置同源的 Secure、HttpOnly、适当 SameSite 会话 Cookie | 受保护写命令须同时通过 CSRF 和精确 Origin 检查；前端不把会话 Cookie 转为可读 Bearer。不能通过任意添加 Authorization 头切换认证模式并绕过 CSRF。 |

会话令牌由密码学安全随机源产生，随机强度采用 research.md 的方案，仅摘要入库。服务端会话记录包含主体、客户端类型、创建时点、最后活动时点和撤销/失效事实。任何受保护请求先校验令牌、账号及期限，再更新合法会话活动时点；不得先刷新再判断是否过期。

Web 的 CSRF 初始化由 `GET /auth/csrf` 完成：匿名调用只签发防伪令牌及预认证上下文，不授予身份，不返回身份或患者线索。浏览器随后以匹配的 `X-CSRF-Token` 调用员工登录。登录成功后轮换会话标识及 CSRF 上下文，写命令采用会话绑定的校验。实现使用 Spring Security 的成熟防护机制；会话 Cookie 的 HttpOnly 属性不因前端需要读取 CSRF 值而关闭。CSRF 令牌、会话令牌及密码均不写日志。登录、身份及 CSRF 响应禁止缓存。

不允许 Web 来源借用小程序客户端模式绕开 Cookie 请求防护；同时携带相互冲突的会话凭据时拒绝，不由客户端指定优先级。小程序 Bearer 模式用于不自动附带浏览器 Cookie 的小程序请求，不能通过伪报角色、患者主键或客户端类型获得权限。

### 精确时限与即时失效

| 条件 | 判定与结果 |
| --- | --- |
| 空闲达到 30 分钟 | 在更新最后活动时点之前判定失效；拒绝当前受保护请求。 |
| 从建立起达到 8 小时 | 不论近期是否活跃均失效；重新登录才能建立新会话，刷新不能延长旧会话绝对寿命。 |
| 连续第 5 次认证失败 | 原子更新失败计数，限制该身份的认证 15 分钟；并发错误提交不能绕过限制。未通过 CSRF 或格式校验不能伪记为已经验证过的密码失败。 |
| 注销、账号停用、诊所撤权 | 状态变更提交后，下一次受保护请求读取主实例当前事实并拒绝原访问，不等待缓存或令牌自然到期。 |
| SF02 旧绑定被撤销/替换 | 旧主体即使仍持有效登录会话，也不得再凭旧绑定访问该患者档案或办理其本人预约。 |
| 身份存储或权限无法核验 | 拒绝受保护操作，不使用历史成功缓存降级放行。 |

请求不得仅凭历史会话快照中的角色、`clinic_scope` 或患者绑定作决定。每次读取权威账号、当前绑定、权限及有效期；成功写命令在事务入口重新检查。注销、撤权或重绑与请求并发时，使用明确的身份/授权记录锁次序协调：已经开始的操作与变更按事务提交顺序处理，变更提交后新开始的请求不能继续使用旧事实。不得将“下一次请求”实现为若干秒的最终一致性窗口。

## SF01 登录与退出

| 路由 | 可信输入与前置 | 成功结果与必要处理 | 失败边界 |
| --- | --- | --- | --- |
| `GET /auth/csrf` | Web 同源访问；不要求已有员工会话 | 签发匿名防伪上下文及 CSRF 值，供员工登录校验；已有会话时验证其上下文并轮换会话绑定防伪值（Session仅存摘要）；不授任何业务身份 | 不开放携凭据的任意跨域读取，不返回主体、账号或患者线索；它是技术防护接口，不是新增业务功能。 |
| `POST /auth/wechat-sessions` | 小程序提交 `wx.login` 临时代码；AppID 与 AppSecret 来自服务端受控配置，不能由请求覆盖 | 后端调用微信 `code2Session`，验证返回结果并取得可信 OpenID，映射内部主体，签发 ADC 小程序会话；返回主体类型、会话期限和是否已有有效本人绑定 | 无效/已使用代码、微信失败、频率限制或本地账号不可用均不建立可信会话；不回传 AppSecret、`session_key` 或原始外部错误中的敏感资料。 |
| `POST /auth/staff-sessions` | 个人账号标识、凭据及 Web CSRF/Origin 条件；账号启用且不处于限制期 | 成熟 Argon2id 库验证凭据，建立员工会话并设置 Cookie；返回员工可见能力与诊所范围的最小投影 | 无效凭据、停用、限制期或组件不可用拒绝；公共错误不能区别泄露账号是否存在。不得自动授予总部能力。 |
| `DELETE /auth/session` | 当前可信会话及对应客户端的写请求保护；携带原请求防重键 | 撤销当前服务端会话，Web 清除对应 Cookie，保存注销审计；提交后下一请求拒绝 | 令牌已无效时仍不允许业务访问；重复退出可以返回统一未认证结果，但不会恢复会话或产生业务变更。 |
| `GET /me` | 有效 ADC 会话 | 返回可信主体类型、当前可用角色/能力、诊所有效范围，以及患者本人绑定的最小状态；信息供界面呈现，不成为下一请求的授权依据 | 无会话、失效或停用返回未认证，不返回患者姓名、编号匹配结果或临床资料；匿名防伪引导由独立 `/auth/csrf` 处理。 |

微信代码交换在本地业务事务之外完成，不持有业务行锁等待外部网络。超时/结果未知时不能据客户端 OpenID 补登；按当前微信代码语义重新发起登录。生产必须使用真实适配器，模拟身份只允许隔离测试配置，生产启动校验拒绝模拟适配器。

## SF02 本人登记 关联与当前关系

微信登录确认平台账号，不自动读取患者档案。首次就诊与已有档案关联是两个独立入口；每个登录主体与每个患者档案同时至多一个有效关联，同账号换设备不算新主体。

| 接口 | 权限与输入 | 成功结果 | 拒绝或限制 |
| --- | --- | --- | --- |
| `POST /me/patient-registration` | 已登录WECHAT患者；仅SelfPatientRegistration及Idempotency-Key；不接受patient_id、患者编号或前台核验字段 | 生成患者编号，新建Patient、自动建立本人映射，保存SELF_DECLARED来源、BIND事件、回执及审计；返回PatientView | 必填资料或本人确认缺失、疑似重复或已有当前映射拒绝；不认领任何旧档案；同键重放仍查当前本人范围 |
| `POST /me/binding-requests` | 已登录患者；仅patient_number/date_of_birth/clinic_id作为已有档案线索 | 保存PENDING申请，不获得历史资料或原患者预约权 | 不自动匹配或覆盖；不返回是否命中他人档案；patient_id不能作为本人凭据 |
| `GET /me/binding` | 有效WECHAT患者会话 | 当前本人映射；无映射明确未关联 | 不按客户端指定主体查询，不恢复旧失效映射 |
| `GET /binding-requests` | 授权前台及服务诊所范围 | 最小申请／登记来源信息；APPROVED只说明已接纳登记或已办理核验，不证明仍为当前关联 | 不扩大诊所或枚举范围外患者 |
| `POST /binding-requests/{requestId}/approve` | 授权前台，已有档案线索、patient_id、verification_basis和原因 | 人工核实后关联既有Patient，整体保存依据、映射、BIND、审计和回执 | 本人不符、双方任一当前关联冲突或申请状态不符拒绝，不覆盖 |
| `POST /patient-bindings/{subjectId}/rebind` | 授权前台；旧主体、新主体、后者PENDING申请及本次核验依据 | 同事务批准新申请、撤销旧映射、建立新映射和REBIND历史 | 新主体已有其他档案或任一步失败整体回滚，旧主体后续不得访问原患者 |
| `POST /patient-bindings/{subjectId}/revoke` | 授权前台，本人解绑依据及原因 | 撤销当前映射并保存UNBIND证据；不删除Patient或预约 | 无权或不能核实则不处理 |

### 首次本人登记

1. wx.login代码由后端使用受控AppID/AppSecret向code2Session交换，精确映射ExternalIdentity→Subject，签发只存摘要的ADC会话；未关联账号可读取活动门店、治疗项目及真实候选，不获得医疗资料或占位。
2. SelfPatientRegistration包含现有Patient必填资料、服务门店、allergy_statement（NONE／KNOWN／UNSURE）、可选allergy_note及consent=true；有过敏史须说明，出生日期不得晚于当前业务日期。患者编号由服务器生成，不要求短信或人工批准。
3. 在同一事务与稳定主体／创建互斥保护下查重、新建Patient、保存BindingRequest和CurrentPatientBinding、追加BIND事件、成功回执与审计。并发同主体最多一个当前档案；相同请求重放同一结果，异内容拒绝。
4. verification_basis由服务器写入method=SELF_DECLARED、person_confirmed=false、allergy_reviewed=false、本人声明及门店。APPROVED在此分支表示系统接纳本人登记。reviewed_by／verified_by沿既有字段保存实际登记主体，verified_at为关联生效时间；名称不代表人工核验，界面使用“已登记／已关联”。不增加技术或业务表字段。
5. Patient.allergy_review_status保持NOT_REVIEWED；声明保存在现有申请／关联事件JSON，不伪造PatientAllergy临床记录。PatientView投影registration_method、self_reported_allergies及SD1当前声明快照引用；患者确认完整声明后可预约。SD1不是医护核实，AR1及已核实过敏链继续按原规则生成、校验；前台不能拿SD1替代其核实依据。
6. 任何失败整体回滚。登记成功响应未知保留原请求查询／重试；映射被撤销或替换后，历史成功回执不得再次返回旧患者资料。

### 已有档案关联与换号

患者只提交档案线索与服务点，不泄漏是否匹配。授权前台依据实际服务核实本人和原Patient，批准时保存patient_id及核验主体、时点、依据。没有档案的患者可使用首次本人登记，前台也可按UC05代办建档；代建本身不自动把历史档案给申请账号。

换号须由新微信独立登录并提交PENDING申请，前台核实后原子替换同一Patient的关联。唯一约束与固定主体锁序保证双向一对一；旧会话即使未过期也失去原患者访问权。解绑不删除档案或历史。服务门店不是Patient永久归属，前台读取及更正仍须逐请求校验岗位和服务依据；不采信客户端clinic_scope、patient_id或自报核验字段。

不新增身份证件上传、短信／邮件认证、亲属代管或支付功能。登记声明与人工核验证据均保留实际来源，技术资料清理遵循保留策略。

### 匿名防伪上下文与隐藏表边界

GET /auth/csrf预认证上下文使用带用途、短期到期时间和随机nonce的服务端签名Cookie，
配合CSRF值与精确Origin验证，不建立匿名业务主体或AnonymousSession表。
登录后轮换ADC Session和防伪值；WEB会话摘要落Session.csrf_secret_hash，会话Cookie保持HttpOnly。
失败认证计数存LoginThrottle，以固定认证域和账号HMAC键原子更新。
已识别员工账号/微信外部身份按账号键处理；微信交换失败且未取得可信OpenID时不能伪认患者身份，
使用服务端实际连接来源（经已配置可信代理校验后的来源）形成匿名限制键，同样执行5次/15分钟限制。
不接受客户端自报IP或OpenID作为可信主体；未知账号与匿名来源的处理不泄露账号存在性。
不启用Spring Session JDBC自动建表，不增加SPRING_SESSION、缓存会话表或Quartz作业表。

## SF03 员工账号及初始化

| 路由 | 执行条件 | 处理及边界 |
| --- | --- | --- |
| `POST /identity/staff-accounts` | 具有账号管理能力的总部人员，已核实工作人员身份 | 创建或关联独立员工主体、个人账号及凭据；牙医适用时关联可信 Dentist 业务标识，不为其他员工伪造 Dentist；创建账号本身不授任何总部业务能力。 |
| `POST /identity/staff-accounts/{subjectId}/activate` | 同上且对象在其可管理范围内 | 保存启用事实及审计；仍须独立存在有效角色/诊所授权才可办业务。 |
| `POST /identity/staff-accounts/{subjectId}/deactivate` | 同上 | 保存停用事实，使其后续受保护请求拒绝；任职、治疗、开票及绩效历史不删除。 |
| `POST /identity/staff-accounts/{subjectId}/credential-recovery` | 同上，且本人/员工核验及恢复依据可追踪 | 按受控方式更新凭据、撤销不应继续有效的旧会话并保存审计；秘密不得出现在日志、回执明文、审计内容或业务表，不擅自引入短信/邮件发送。 |

初始管理账号由后续实施阶段的受控初始化命令创建，不提供匿名总部注册，不在仓库或镜像预置固定账号密码。初始化记录操作者和授予范围；重复初始化不能自动增加权限。具体账号标识、实际秘密由环境管理者在部署时提供，Plan 不填写假凭据。

密码散列算法使用成熟实现，参数及版本受控；需要性能测量的参数按 research.md 落实。凭据校验和更新不得降级成通用快速散列或明文比较，也不得把 Patient.phone 或 Dentist.employee_number 本身视为登录秘密。

## SF04 能力 诊所范围与对象检查

| 路由 | 执行条件 | 必须保存及校验 |
| --- | --- | --- |
| `POST /identity/grants` | 已授授权管理能力的总部人员 | 目标账号、岗位/操作能力、诊所范围、有效期及变更依据；授予范围必须属于操作者可授予范围，不能自报更大范围。 |
| `POST /identity/grants/{grantId}/revoke` | 同上且有权管理该授权 | 撤销事实及可信审计；提交后下一次请求重新读取授权并拒绝原范围操作。 |

每次受保护请求组合判断：可信主体 → 账号/会话可用 → 对应操作能力 → 当前有效诊所范围 → 目标对象实际所属诊所/本人关系 → 岗位所需字段。任何一项不能验证即拒绝；授权路径本身同样执行完整检查。

总部能力至少区分资源维护、普通分析、成本核验、绩效复核发布、敏感下钻、员工账号管理、诊所授权管理及审计查询。分离是逐项能力检查，不擅自增加“两个不同自然人必须办理”的新政策。“医生”对应既有牙医角色；“诊所管理员”是员工 Web 入口称谓，其实际操作由既有岗位能力组合与诊所授权决定，不因名称获得总部权限。

患者可首次登记新本人档案并通过当前本人关联操作 UC01-S1/S3；前台按授权服务范围处理 UC01-S1—S5、UC02、UC05 及 SF02 核验；牙医记录本人实施、获授权且资质/执业有效的实际治疗；收费仅访问结算必需资料。总部普通分析默认汇总，患者风险资料仅提供实际接诊岗位所需内容。

接口响应采用不同岗位的显式投影，不先返回完整临床对象再交前端隐藏字段。患者或未授权员工请求他人对象时，公共错误不得泄露对象是否存在、姓名、电话、过敏资料或金额。

## 可信防重及操作上下文

所有受保护写命令都携带 `Idempotency-Key`；令牌、角色及诊所范围不能嵌入该键作为可信身份。业务服务从已验证上下文取得主体，按主体、操作和请求键查 `adc_identity.RequestReceipt`，并比较规范化请求内容摘要。相同内容返回原处理结果或对象引用；同键不同内容拒绝覆盖。

命名锁、事务连接及释放时点遵循 research.md R-D03：在同一物理连接取得互斥，事务提交或回滚真正完成后释放，连接归池前完成清理。不得仅用 JVM 锁、前端按钮防抖或 AppointmentEvent 的组合唯一键防止重复创建。

查回执前也必须校验当前身份、授权和对象可见性。旧绑定已经失效、账号被停用或权限已撤销的调用者，不能凭过去成功的请求键取回旧敏感响应。回执保存对象标识及最小结果，不复制密码、微信密钥、完整患者档案或临床备注。可信 `request_id` 用于审计关联；客户端自报 `X-User-Id`、`X-Role`、`X-Clinic-Scope` 等头不构成身份上下文，网关也不能未经认证直接透传为可信主体。

## 审计与失败提交规则

| 类型 | 提交要求 | 返回条件 |
| --- | --- | --- |
| 资料更正、绑定/授权、取消、成本冲销、绩效发布等规定成功写操作 | 在同一连接及事务保存业务/身份事实、必要事件、成功回执和审计；身份重绑两端事实也整体提交 | 审计未持久化不得报告写操作完成；失败全部回滚，允许原键按规则重试。 |
| 敏感读取及审计查询 | 校验专门权限并保存读取审计；审计只记目标/范围和结果，不复制完整临床内容 | 审计持久化后才返回敏感结果；审计不可用不绕过。 |
| 被拒绝或回滚的请求 | 不产生成功业务/回执；在原事务回滚后，以独立短事务追加失败/拒绝审计 | 错误响应保持拒绝或失败，不以审计写入改变业务失败结论。 |

每条可信审计至少包含：服务端取得的主体、动作、目标对象、诊所/数据范围、服务端发生时间、请求标识、结果及原因。绑定更正另保留核验依据，患者过敏更正仍保存 PatientAllergy 原核实链，生命周期仍保存 AppointmentEvent，绩效发布仍保留 source_snapshot 和版本，不用通用审计替代原业务证据。

`GET /audit-events` 仅有审计查询权限的总部人员可用，并校验被授范围及最小字段。支持按操作、对象、范围、期间及请求标识查证；不允许普通账号编辑或删除。审计保留 1 年，备份与恢复必须覆盖保留期内证据；30 天备份窗口不能被解释为审计只保留 30 天。

业务、身份技术（含控制与迁移历史）、审计三个schema必须纳入同一一致性全备和同一 binlog 恢复位点。恢复后核对当前绑定双向唯一、旧绑定失效、账号及撤权状态、审计与已提交事实对应；不能把不同时间点的身份和业务备份拼接后宣称恢复一致。

## 错误与信息披露

具体错误码以公共 API 注册表为准；本文规定客户端可以依赖的分类：未认证/失效为 401，已认证但无权或 CSRF 不通过为 403，绑定或同键内容冲突为 409，输入不合法为 422，认证限制为 429，不能核验身份或关键依赖不可用为 503。响应不包含密码、会话令牌摘要、密钥、原始 SQL、患者存在性探测结果或无关临床信息。

前端只对可更正输入作提示；对超时未知的受保护写请求，保留原键查询或重试，不能换键再次批准、重绑或授予权限。外部微信故障与非法代码需可区分供可信运营排障，但患者响应不泄露外部秘密。
