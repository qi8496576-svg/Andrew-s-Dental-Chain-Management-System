# Andrew's Dental Chain（安德鲁牙科连锁管理系统）Constitution

本宪章规定 ADC 项目的需求、业务、数据、架构、质量和开发流程边界。
“必须”“不得”为强制要求，适用于人工及自动化开发、评审和验收。
它规定如何落实和变更已确认资料，不代替用例规约、数据字典或功能 Spec。

## Core Principles

### I. 需求一致性与资料可追溯

- 业务依据必须是最终定稿的《安德鲁牙科连锁管理系统需求分析与设计》Word。
  当前权威文件为项目根目录同名 `.docx`，归档身份见 S1。
  `docs/requirements/` 的 A—D 四章是检索副本，不具有独立修改业务规则的效力。
- 图面必须以最终 Word 实际嵌入的正式图为基线，结合正文完整契约解释。
  独立 SVG、PNG、操作 JSON、重建 PlantUML/Mermaid/DBML 和历史修订稿
  必须按 S4 的来源说明使用，不能凭文件名、文件时间或旧编号认定正式采用。
- 每项功能必须建立“原文章节及表号 → UC/SF/场景与规则 → UML/状态模型 →
  关系模式与字段 → API/代码 → 验收与测试”的追踪关系；只读或身份功能无业务表映射时
  必须明确说明，不能为补齐映射而虚构业务表。
- 不得为实现便利更改已确认的流程、权限、状态、指标或 R1 规则。
  变更必须经 Governance 规定的审批，并同步核对受影响的需求、模型、数据及测试。
  原始 Word、UML 和归档资料不得在未获明确授权时覆盖或改写。

理由：统一事实来源和追踪关系，防止历史候选资料或实现选择造成需求漂移。
依据：S1—S4、S6—S7；原件保护同时来自 S8。

### II. 业务规则、身份与权限不可绕过

- 系统业务范围必须沿用八项用例：UC01 预约就诊、UC02 管理出诊排班、
  UC03 记录治疗、UC04 结算就诊、UC05 维护患者资料、UC06 维护组织资源、
  UC07 核算季度绩效、UC08 运营分析。
- UC01 必须分别落实 UC01-S1 创建预约、UC01-S2 确认到诊、UC01-S3 取消预约、UC01-S4 登记爽约、
  UC01-S5 停诊改约的执行者、前置条件、扩展路径和后置条件。
  历史图源 UC09—UC12 依次对应 UC01-S2、UC01-S3、UC01-S4、UC01-S5，不得增加四个独立系统用例。
- 就诊只使用 SCHEDULED、IN_PROGRESS、COMPLETED、INVOICED、CANCELLED
  五种状态。必须先到诊再记录治疗，至少存在一项有效诊疗项目才可完成，完成后才可结算。
  取消只适用于 SCHEDULED；NO_SHOW 是取消分类，不是第六种状态。
  到诊、完成及结算后不得取消；已取消对象不得恢复，改约必须新建预约并保留来源链。
- 患者自助取消必须早于预约开始且班次正常；开始至时隙结束由前台核实代办；
  时隙结束后经前台核实未到诊才可登记 NO_SHOW，不得由定时任务直接认定爽约。
  停诊只挂起班次，受影响预约经 UC01-S5 处理；CLINIC_RESCHEDULE 与 CLINIC_CANCEL
  必须单独分类，不计入患者主动取消和爽约率。
- 预约必须校验已核验且当日有效的必需资质、执业关系、正常班次及占位；
  实际治疗必须校验实施牙医在治疗日的有效资质及诊所执业关系。
  预约期望治疗不得冒充实际治疗；每项实际治疗必须保存实施牙医及历史价格。
  实施牙医可与预约责任牙医不同，收入必须逐项归属实际实施者。
- 首次患者可在微信登录后填写姓名、出生日期、联系电话、过敏声明并确认，由系统自动生成编号和关联新档案，直接预约。
  本人过敏声明保持 NOT_REVIEWED，允许以 SD1 当前声明引用确认本人预约，不冒充 AR1 医护核实；
  已有档案关联、换号和受保护资料更正仍须安全核实，不自动认领历史资料。
- UC04 仅核定费用并生成唯一费用凭据。演示支付和全额退款使用独立账单、支付与退款记录，不扣真实款；真实收款、渠道对账、
  税费或折扣须另行批准；INVOICED 不表示已付款。重复结算必须返回原单，开票后治疗及明细只读。
- R1 必须按开票时点归集收入、按成本发生时点归集成本；自然季度按 Asia/Shanghai
  解释，采用起点包含、终点不含的区间。必须纳入任职区间与季度相交的牙医及当季
  存在收入或成本归属的其他牙医，包括离职和无收入人员。
  公共运营费用必须按同诊所、同季度、任职及执业有效区间内 NORMAL 班次分钟数分摊，
  排除 SUSPENDED；不得改按营业额、治疗次数或平均人数分摊。
  个人净利润＝收入－医疗用品成本－运营费用；个人激励＝ROUND(MAX(个人净利润,0)×0.10,2)。
  非正净利润激励为零，资料完整即可复核发布；不得生成负激励或跨季扣减。
  缺少封账、零成本确认、成本归属，或有待分摊净额但有效总时长为零时，
  必须保存 INCOMPLETE 和具体原因并禁止发布，不得把缺失当作零。
  计算与复核发布必须分离，同一牙医同一季度至多一个当前 PUBLISHED 版本，历史依据可查。
- UC08 必须沿用表 A1a、B13 的期间、队列、截止时点及口径版本，列明排除与缺失数量。
  未处理预约单列并使相关结果标为暂定；分母为零返回不可计算。
  治疗比较使用同一单位定义下的加权单价，技能时隙覆盖率不得替换为未占用时隙比例。

身份与权限必须遵循 SF01—SF04 和表 B12a、D26：

| 支撑功能 | 强制要求 |
| --- | --- |
| SF01 登录与退出 | 患者小程序登录、员工个人账号登录；服务端校验可信主体和会话，退出注销，无效身份拒绝访问。 |
| SF02 登记与关联本人档案 | 已登录患者首次填写本人资料及过敏声明并确认后，由服务器生成编号、新建档案并自动建立 subject_id 与 patient_id 关联，无需人工批准；已有档案不得按姓名或手机号自动认领，关联、换号、解绑、重绑及冲突由授权前台安全核实并留痕。 |
| SF03 管理员工账号 | 仅授予账号管理权限的总部人员办理；员工业务资料不等于登录账号，不得自动取得总部权限。 |
| SF04 分配诊所权限 | 仅授予授权管理权限的总部人员在自身可授予范围内配置角色、诊所和有效期；每次受保护请求必须复核有效授权。 |

患者仅可操作当前有效关联的本人资料及 UC01-S1、UC01-S3；首次本人登记自动关联新档案，已有档案须安全核实；前台仅可在授权诊所服务范围执行
UC01-S1、UC01-S2、UC01-S3、UC01-S4、UC01-S5、UC02、UC05，跨诊所复用资料必须有服务依据；牙医仅可访问获授权就诊及
风险资料并记录本人实施治疗；收费人员仅可访问授权诊所结算所需资料；总部的资源维护、
分析、成本核验、绩效发布、敏感下钻和账号授权管理必须分别校验权限。
所有 API 必须检查功能权限与对象归属，不采信客户端自报 patient_id、角色或 clinic_scope。
越权请求不得泄露敏感信息或改变业务记录，身份或授权无法验证时必须拒绝受保护操作。

理由：统一生命周期、核算口径和可信身份，保证患者本人隔离及员工职责边界。
依据：S1—S5，重点为表 B3—B13、C2—C3、D22—D26 和图 B1、C4—C16。

### III. 数据模型、历史证据与精确金额

- 业务数据库必须以最终 ERD、关系模式及数据字典为准；当前基线是 24 张表、
  209 个字段、44 条外键，结构逐项对应表 D3—D21：
  Patient、Allergy、PatientAllergy、Clinic、Dentist、Qualification、DentistQualification、
  DentistClinicAssignment、DentistSchedule、Treatment、TreatmentQualification、Appointment、
  AppointmentRequestedTreatment、AppliedTreatment、Invoice、InvoiceItem、CostEntry、
  QuarterlyPerformance、AppointmentEvent、RegistrationFeePolicy、BookingHold、PatientBill、PaymentOrder、RefundOrder。
- 必须保留已确认的表、字段、数据含义、精度、可空性、主外键、唯一性和完整性约束。
  19 张表采用单列代理主键，5 张表采用复合主键；业务编号与存储主键必须分离。
  身份、会话、绑定及授权独立存储，不得为登录擅改 24 张业务表，
  不得将前台、收费或总部人员伪造为 Dentist。
- DBML 只表达部分结构，必须共同执行表 D22—D24 及 constraints.md。
  条件唯一不得变成全局唯一，JSON 来源快照不得伪造为直接外键。
  跨诊所正常排班不重叠、有效时隙不重复占用、同次就诊唯一开单、实际治疗不重复开票、
  改约同患者无环且至多一个直接后继、成本冲销及发布唯一性必须有领域和事务保障。
- 不得为开发便利或因目录调价删除或覆盖被引用的班次、取消及改约轨迹、过敏更正证据、实际治疗历史价格、
  开票快照、已确认成本、就诊事件或绩效历史版本。目录停用必须保留引用；
  过敏误记撤销必须追加核实信息，不得将空关联推断为 NO_KNOWN，也不得按手机号自动合并患者。
  成本纠错必须依规冲销后补记；发布新版时保留旧金额与来源并将旧发布版置为 SUPERSEDED。
  开票前的价格纠错仅限经授权核实并留痕的处理，牙医不得自行覆盖单价。
- 金额及其计算必须使用精确十进制类型，单位数、单价及激励率保持数据字典规定精度。
  数据库存储必须采用数据字典规定的 DECIMAL(p,s) 或经批准的等价精确类型。
  不得使用二进制浮点近似值作为计价、分摊或核算依据；API 传输必须保持精度。
  治疗小计按十进制四舍五入到分后累加，总价等于明细小计之和。
  公共费用尾差必须遵循 Word 第四章第十五节：按净额绝对值分摊、向下截到分，
  余分按未舍入余数降序分配，同余按 dentist_id 升序，再恢复净额符号；
  分摊合计必须守恒且不得重复计入。
- 业务时间必须按 Asia/Shanghai 解释，存储时间点统一转为 UTC，日和季度边界按业务时区计算。
  获批的数据设计变更必须给出逐字段影响、迁移、历史保全和核验方案，不得静默漂移。

理由：让诊疗事实、金额及核算证据在重试、纠错、调价和版本变更后仍可追溯。
依据：S1、S3—S5；精确十进制和历史保护同时落实 S8。

### IV. 双端统一服务与可部署架构

- 患者端必须是微信小程序，工作人员端必须是 Web 管理后台，两个前端必须使用同一后端
  业务 API。业务状态、计价、资质、归属和分摊规则必须在统一服务端执行。
- 必须保持表示层、应用层、领域层、基础设施层的职责：表示层负责输入输出，
  应用层编排用例、授权与事务，领域对象和领域服务执行不变式及计算，
  数据映射器负责持久化。领域层不得依赖前端或具体数据库实现；
  控制对象不得承揽本属领域对象的金额计算，报表采用经授权的只读投影。
- 身份组件必须满足表 D26，并与业务存储分离；独立组件不等于预先要求微服务部署。
  对外接口必须按用例提供操作，不得开放任意状态改写或由前端自行决定业务成功。
- 最终部署目标必须是 Linux + Docker。后续 Plan 必须说明容器运行、配置及秘密管理、
  持久化、迁移、备份恢复和日志方案；本次不生成部署文件。
- 具体语言、框架、数据库产品与版本、身份产品、ORM 及测试工具必须在后续 Plan 中
  结合约束和验收条件比较、说明并经评审确定，本宪章不提前选型。
  原 Word 和 DBML 的 MySQL 表述作为既有设计背景保留，按 C-02 处理，
  不得据此忽略本次“技术栈留待 Plan”的明确约束，也不得静默丢弃原结构及语义。

理由：两个入口复用同一规则，同时保留实现选型空间和明确的部署目标。
依据：S1、S3—S4 的图 D2 及第四章第九至十四节；Linux + Docker 和选型时点来自 S8。

### V. 自动化验证、事务与数据安全

- 核心业务逻辑必须有自动化测试，覆盖正常、边界和失败路径。
  必测范围包括 UC01 五场景及非法迁移、资质与跨诊所排班冲突、患者隔离和员工越权、
  重复请求与并发占位、历史价格及逐项舍入、唯一开单与故障回滚、R1 人员范围、
  分摊尾差与守恒、零及负利润、不完整禁止发布和并发切换唯一发布版本。
  领域测试必须可独立验证规则；涉及数据库锁、唯一键和原子性的行为必须有集成验证，
  不能仅用模拟对象或界面演示宣称通过。
- 创建预约、状态迁移、停诊改约、结算及绩效发布必须有明确事务边界，
  主记录、关联、明细、状态事件必须整体提交或回滚。
  锁定顺序和范围必须满足表 D22、D25；首次发布必须锁定稳定存在的 Dentist 行。
  幂等必须基于可信主体、请求标识和请求内容；AppointmentEvent 的组合唯一键
  不能单独解决重复创建预约。超时结果未知必须用原请求标识查询或重试。
- 必须落实认证、授权、字段最小披露、加密通道和可信审计。
  资料更正、绑定及授权、取消、敏感查询、成本冲销和绩效发布必须记录主体、对象、
  范围、时间、请求标识、结果及原因；规定写操作的审计未持久化不得报告完成。
  普通账号不得修改或删除审计，日志不得记录认证秘密及无关完整临床资料。
- 必须逐项继承 Q01—Q09 及表 B12 的测试条件，不得自行降低门槛。
  会话空闲 30 分钟或建立满 8 小时失效；连续 5 次认证失败限制 15 分钟；
  注销、停用和撤权后下一次受保护请求即拒绝。审计保留 1 年，仅审计授权人员可查。
  每天全量、每 15 分钟增量备份，保留 30 天；RPO≤15 分钟，RTO≤4 小时，
  恢复必须核对业务、身份、绑定、授权及审计的一致性。
- 开发、自动化测试、演示和验收数据必须为虚构患者数据，不得复制真实患者记录、
  联系方式或临床资料进入开发资料、日志或测试夹具。测试环境必须与正式数据隔离。
  验证证据必须记录环境、数据集、步骤、期望与实际结果及核验人；
  未执行的检查必须标明未执行，不得以代码存在、文档声明或低于基准的环境替代通过证据。

理由：用可复核证据保障并发、核算和敏感资料操作的正确性及可恢复性。
依据：S1—S5 的 Q01—Q09、表 D22—D26；自动化测试及虚构数据来自 S8，S7 支持测试追踪形式。

### VI. 规范先行、明确验收与冲突停工

- 每项功能必须依次完成 Specify → Clarify → Plan → Tasks → Analyze，项目负责人审核通过后才能 Implement。
  Clarify 必须消除影响业务、权限、数据及验收的关键歧义；即使没有待澄清问题，也必须记录核对结论。
  Plan 和 Tasks 必须检查本宪章，标明需求来源、依赖、数据与接口影响、测试和验收任务。
- Tasks 完成后必须执行 Analyze 跨文档一致性分析，检查 Constitution、Spec、Plan、Tasks、
  原始需求及 UML/ERD 之间的冲突、遗漏和不一致，记录问题、严重程度、来源、影响及处理结论。
  存在未解决的关键问题时不得进入 Implement；修订受影响文档后必须重新分析。
  Analyze 完成后必须提交项目负责人审核，不得以分析工具完成代替审核通过。
- 审核必须由项目负责人（当前用户或其明确授权的审核人）对具体版本留下明确通过记录，
  包含范围、文档版本、Analyze 结论和未解决项。资料存在、工具自动完成或没有收到反对均不构成实施许可。
  审核后的实质需求、权限、模型或验收变化必须重新评审受影响范围。
- 每项功能必须有可判定通过或失败的验收标准，覆盖执行者、前后条件、主路径、
  扩展与失败路径、权限、数据完整性以及适用质量目标，并关联可执行的验收步骤或测试。
